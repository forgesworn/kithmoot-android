# Native invitation generations and replacement

The selected native host can replace an ACTIVE or fully retained RETIRED
invitation from Room details. Confirmation binds the actual owner, source
revision, traffic epoch, lifecycle and invitation generation. A changed
observation requires a fresh confirmation. Existing approved members keep
their traffic keys and device registry; a new invitee still needs current-epoch
approval. Replacement does not rotate the room's traffic epoch.

## Durable transaction

An explicit replacement transforms a verified schema-5 source with its marked
courier to schema 6. Read-only opening does not migrate it. The record retains
its current invitation and all prior generation material needed to validate
unexpired original answers. Cached invitation answers name their generation;
historical answers cannot be offered through a new generation. The base room,
root signer, traffic epoch/cause, approved and removed devices remain unchanged.

Private preparation consumes the source's one-use preflight handle. Before
entropy or signing it checks the exact current index, policy, signing/spending
budget, archive reservation and unsigned pending/completed file layouts. Both
layouts include retained history/caches, a full bounded spend array, maximal
original maps and reference/link overhead. This is a source capacity check,
not evidence that every capacity boundary has been measured.

One atomic source write retains the new welcome and required old notice before
offers or index changes. Old admission and all sharing stop at that write.
ACTIVE replacement signs one old notice and one new welcome; RETIRED replacement
reuses its exact archived notice and lifetime counters without automatic resend.
Each reserved offer is charged before dispatch. Nearby does not publish a
standalone welcome. Internet/Mixed require the exact staged welcome's existing
local relay-custody condition. This does not confirm participant storage.

The actual RoomRepository conditionally installs the retained proposed link and
version-2 reference, merging unrelated current room metadata under its monitor.
Read-back precedes the source's index acknowledgement. Actual invitation
collectors then register the proposed generation's filters on the already
selected routes; their owned registration callbacks precede source completion.
Current-epoch collectors remain bound to the stable room/root. Old callback
authority is invalidated before its collectors are cancelled and joined.

Sharing in Room details and Home reads the actual index and verifies it against
the selected source and observation. It does not reuse the URL captured when
the room opened. A completed generation with a rolled-back old index refuses.

## Cold recovery and bounds

Entry opens source/index and the real marked receiver/courier before any route.
A pending replacement accepts only its exact retained previous or proposed
index for the same owner/profile. It resumes the same originals and repairs an
index-installed transaction before routes open. Missing, corrupt or unrelated
stores are not recreated for fresh retry credit. An ambiguous source-write
return withdraws the owner; a new owner inspects the committed original file.
Schema 6 with generation zero and no real pending transaction refuses.

History is bounded to fifteen replacements, retaining the sixteenth retirement
archive slot for terminal closure. Historical nonterminal notices can be
explicitly resent while the current invitation remains ACTIVE, conserving their
original attempts and spending. History is not evicted to grant another
replacement. Joint rollback resistance across source and index is not claimed.

## Evidence boundary

The mesh-kit lab records exact source hashes and local JVM measurements of
multiple generations, oldest cached-answer reopen, historical resend, pending
and ambiguous writes, strict malformed-record refusals, index-qualified sharing,
archive reservation and selected transport modes. Fresh Compose/instrumentation
compilation is distinct from rendered emulator execution.

CI adds three rendered production ViewModel/control journeys: Nearby and Mixed
two-generation replacement with a prior rekey and approved offline device, and
Mixed pending replacement across encrypted reopen. The full runner still
requires all prior suites, six numeric retired-store refusals and eight existing
external SIGKILL/new-PID drivers. No predecessor gate qualifies this candidate.

Full acceptance additionally needs every remaining bound/refusal and listener
failure/reconnect case, actual paired current-epoch admission in all modes, and
the five replacement-specific external kill windows from the source-bound
mesh-kit design. Those windows are not simulated by stop/reopen, a thrown write
or the eight older drivers. Physical BLE/RF, MESHSPASTIC backhaul and participant
receipts remain separate measurements; this work authorises none of those.
